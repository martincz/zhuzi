# Quick Roundtable 示例

输入：

```text
/zhuzi:roundtable 给现有 API 增加缓存层，目标是降低 p99 延迟，但不能改变响应语义。当前规范只说同样请求应有同样响应，未定义身份和数据版本是否算输入。
```

以下是假设方案的短读示例，不代表已测得性能提升。具体验证命令与通过标准须在实际项目锁定。

默认输出形态：

## 主持人结论

建议先做小范围缓存，不直接上全局缓存层。当前最大风险不是性能，而是缓存键和失效边界不清，容易把错误结果稳定化。

## 议题卡

**目标**：产出一张决策表，含缓存该怎么落地（locked）/ 不做什么（deferred）/ 如何验证真的做到（验证信号）

**召开席位**
- `linus-engineer` · 架构和实现边界
- `feynman-reviewer` · 缓存响应等价条件未定义，影响合同可验证性

**弃权席位**
- `munger-reviewer` · 本题是接口与工程决策，没有独立的激励或商业取舍
- `taleb-reviewer` · 无尾部风险建模核心问题
- `lopezdeprado-reviewer` · 无研究方法论核心问题

**暂不讨论**
- 不重写整个 API
- 不引入分布式缓存集群

## 席位短评

| 席位 | 结论 | 最大风险 | 必须满足 | 分歧 | 信心 |
|---|---|---|---|---|---|
| Linus | 可做 · 先定义 key 和失效规则 | 缓存键跟业务语义耦合不清，会制造特殊情况 | 先定义 key/TTL/失效入口再写代码 | 无 | medium · 缓存边界尚待核实 |
| Feynman | 可做 · 先定义响应等价条件 | “同样请求”的输入范围未定义 | 写出身份、数据版本和状态变化的例子与边界 | 无关键分歧 | medium · 缺少等价条件 |

## 做完会怎样

若目标 endpoint 确实有可复用的昂贵计算，缓存可能降低 p99；需要在相同负载下验证，但真正的价值在副产品：定义缓存键的过程会逼你把"响应是否由这几个输入唯一决定"写清楚，很多隐式假设会被挖出来暴露。不会做到的：全局查询加速、跨服务数据共享、写请求的一致性保证。那些要另开议题。

**验证信号**：缓存开启后，对相同业务状态、身份和请求分别比较缓存开关下的响应，并检验状态变化后的失效；在相同负载下比较 p99。通过仅说明已覆盖的测试条件成立，不证明全部语义或未来性能。

## 决策表

| 分类 | 内容 | 下一步 |
|---|---|---|
| `locked` | 只缓存幂等 GET<br>缓存键必须包含影响响应的全部输入<br>失效规则写进同一模块 | 进入实施前确认具体 endpoint |
| `deferred` | 不做跨服务缓存<br>不引入新基础设施 | 另开议题评估 |
