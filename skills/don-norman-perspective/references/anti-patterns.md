# Don Norman · UX 反模式清单（Anti-patterns）

> 本文件是 `don-norman-perspective` 的反模式扩展参考。SKILL.md 里列出了反模式的骨架；本文件给出**识别信号、典型样本、修复方向**。
>
> 每条反模式都配一个识别问题——遇到任何一段 UI / 设计描述，把这些问题套上去，通常能在 30 秒内定位到问题类型。

---

## 1. Norman Door

**定义**：从外观无法判断推还是拉的门。在 UI 上等同于"按钮看起来像 X 但其实做 Y"——signifier 给了错误线索。

**识别信号**：
- 按钮 / icon 的视觉提示和实际功能不一致
- 用户必须"试一下"才知道某个交互的方向（点 vs 长按、左滑 vs 右滑、tap vs swipe）
- 同一类元素在不同位置行为不同（同样的"X 按钮"有时是关闭、有时是删除、有时是返回）
- 有横向把手却需要竖向推、有圆形按钮却需要拖动

**典型样本**：
- iOS 控制中心的 toggle——同一个图标，长按和点击是完全不同的动作
- 网页表单的 "Submit" 按钮长得像 disabled 状态（灰色 + 圆角）
- 公共大门：贴着"PUSH"的标签，但门把手是横杠（横杠的物理 affordance 暗示推；竖把手暗示拉）——结果是双重信号矛盾

**Norman 的检查问题**：
- 用户第一次见到这个元素，能不能在不试错的情况下知道怎么操作？
- 视觉提示（signifier）和实际行为（affordance）一致吗？
- 删掉所有标签和文字，剩下的视觉元素本身能不能传达正确的操作？

**修复方向**：
- 把视觉提示和功能强对齐：横把手 = 推、竖把手 = 拉、圆按钮 = 点、长条 = 滑
- 一致性优先：同一类元素在所有位置行为相同
- 如果必须用同一元素表达多种功能，加可见的 second signifier（长按提示、操作菜单）
- 标签是补丁不是修复——好的 UI 不需要"PUSH" 标签

## 2. 隐形手势（Invisible Gestures）

**定义**：UI 提供了某个交互能力，但**没有 signifier 暗示**它的存在。Discoverability 的杀手。

**识别信号**：
- 长按、3D Touch、力度感应、左右滑、上下拉等手势没有任何视觉提示
- "高级用户才知道"的功能藏在不可见的交互里
- 文档里写"swipe right to archive"——但 UI 上没有任何提示
- iOS 上的 "tap the top of the screen to scroll up"——没有 signifier，只有口口相传

**典型样本**：
- iOS Mail 长按邮件 = 弹菜单；普通用户永远发现不了
- iPhone 删除主屏 app：长按图标晃动（再点 X 或拖到删除区）——这条是经典 hidden gesture
- macOS Finder 的 "Quick Look"（按空格键预览）——没有按钮提示
- 网页上的"双击编辑"——用户永远不会双击一个看似只读的字段

**Norman 的检查问题**：
- 这个交互有视觉提示（signifier）吗？
- 一个从没用过的人，能不能在没有教学的情况下发现这个功能？
- 如果这是个核心功能，为什么藏起来？如果不是核心功能，为什么放进来？

**修复方向**：
- 高频功能必须有可见 signifier：图标、按钮、提示文字
- 隐形手势只能用于**冗余加速**（专家用快捷方式），不能是**唯一路径**
- 第一次进入的用户应该看到 onboarding 提示（但不要靠 onboarding 解决 discoverability 问题）
- 长按、双击、3D Touch 永远是 nice-to-have，不能是 must-have

## 3. 空洞反馈（Empty Feedback）

**定义**：用户做了动作之后，系统**没有反馈、反馈延迟、反馈不可解读**。Gulf of Evaluation 的典型失败。

**识别信号**：
- 点击后界面没有任何变化（用户不知道是没收到还是在处理）
- 转圈圈但不告诉进度 / 不告诉预计时间
- "Error 4032"、"Something went wrong, please try again"——这是把评估鸿沟原封不动甩给用户
- "操作成功" toast 但不告诉成功了什么（保存了哪条？删除了哪一项？）
- 自动保存了但 UI 上看不出来

**典型样本**：
- 网页表单提交：点了 Submit，按钮变灰，5 秒后才显示结果——用户已经点了第二次甚至第三次
- 文件上传：进度条卡在 "Uploading..." 不动，用户不知道是真的在传还是已经死了
- 银行 app 转账：点了"确认"——白屏 10 秒——然后跳到"成功"页面。用户中途已经焦虑到要打客服
- 错误信息 "An unexpected error has occurred"——这不是反馈，这是侮辱

**Norman 的检查问题**：
- 每个动作之后界面有没有可见变化？
- 延迟 > 100ms 有没有 progress 提示？
- 错误信息是否 specific（告诉用户具体哪里错了、怎么修）？
- 如果用户中断 5 秒回来，能不能立刻判断当前在哪一步？

**修复方向**：
- 即时反馈：点击 → 按钮立即视觉变化（按下态 / 高亮）
- 延迟反馈：> 100ms 显示 spinner；> 1s 显示 progress bar；> 10s 显示预计时间
- 错误信息必须 specific："密码缺少特殊字符" > "密码无效" > "Error 4032"
- 完成反馈必须 specific："已保存 'Doc-2026-04-26.pdf' 到 Downloads" > "Saved"

## 4. 错误的 Conceptual Model（Wrong Model）

**定义**：System Image 给用户暗示了 X，但系统实际行为是 Y。用户的 mental model 错不是用户的错——是 System Image 在骗人。

**识别信号**：
- icon 的隐喻和实际功能不一致（云朵图标但其实存本地）
- 文案承诺 X 但实际做 Y（"私密分享"但其实可以被搜到）
- 命名误导（"删除"按钮其实只是隐藏，文件还在）
- 用户反复问"这是什么意思 / 这个会怎样"——说明 conceptual model 没传达

**典型样本**：
- iCloud 的"删除"——iPhone 上删除是同步删除还是只删本地？大部分用户不清楚
- 网盘的"分享链接"——是公开链接还是仅特定人可访问？默认设置是什么？
- "记住我" checkbox——记住什么？用户名？密码？session？多久？
- 隐私设置里的"仅好友可见"——好友的好友算吗？平台员工算吗？

**Norman 的检查问题**：
- 设计师脑中的模型（Design Model）和 System Image 一致吗？
- System Image 给用户暗示了什么？这暗示和实际行为一致吗？
- 用户反复犯的 mistake，是不是因为 System Image 在错误地引导？

**修复方向**：
- icon / 命名 / 文案必须对齐实际行为——不要为了"看起来友好"而误导
- 用户行为有不可逆后果时，必须明确告知（"删除将无法恢复" + 多步确认）
- 默认设置必须符合最保守的用户预期（隐私 default = 最严格）
- 让 System Image 主动教 mental model：tooltip、inline 提示、第一次使用的解释

## 5. 强迫记忆（Memory Tax）

**定义**：UI 要求用户在头脑中维持状态、记住步骤、记住自己刚才填了什么。Knowledge in the head 的过度依赖。

**识别信号**：
- 多步流程中，前面填的内容在后面看不到
- 错误信息出现在"提交后"，不是在"出错时"
- 让用户记住 17 个快捷键 / 多个状态 / 多个 mode
- 中断后回来，无法立刻知道当前在哪一步
- "请记住您的预约号 #847291" 然后没有把这个号发给用户

**典型样本**：
- 报税软件多步表单：第 5 步报错，但报错信息只说"第 2 步有错"——用户必须翻回去找
- 多步注册流程：填到第 4 步发现密码不符合规则，但密码在第 1 步——前面已经清空
- Vim 的 mode：用户必须在头脑里维持"我现在是 normal mode 还是 insert mode"
- 银行短信验证码：让用户记 6 位数字然后切到 app 输入
- 软件设置面板：每个设置改变后没有"已保存"提示，用户不知道有没有生效

**Norman 的检查问题**：
- 这个 UI 要求用户记住什么？这些记忆能不能外化到世界里？
- 如果用户中断 5 分钟回来，能不能立刻接着上次操作？
- 错误能不能在出错时立刻提示，而不是延迟到提交后？
- 状态有没有可见？（mode、保存状态、当前选择、当前步骤）

**修复方向**：
- inline validation：错误在出错时立刻显示，不是提交后
- 持久化中间状态：自动保存草稿，让用户中断后能回来
- 状态可见：mode 在 status bar 显示、保存状态在 title 显示、当前步骤在导航显示
- 短信验证码 → 自动填充
- "记住我" → 自动登录
- 任何要求记住 > 7 个东西的 UI 都是失败

## 6. 培训替代设计（Training as Design Cop-out）

**定义**：把 UX 失败用培训 / 文档 / onboarding 掩盖。"用户不会用" → "我们做培训" → 设计永远不改。

**识别信号**：
- 团队讨论可用性问题时，第一反应是"做更好的文档 / 培训 / onboarding"
- "用户没仔细看 tooltip" / "用户没读说明书" / "用户没参加培训" 成为问题归因
- 必须提供长篇 onboarding 才能让用户开始用
- 文档 / 帮助中心比 UI 本身还复杂

**典型样本**：
- 企业软件（SAP、Workday、Oracle）—— 必须培训才能使用，而不是设计成"开箱即用"
- 复杂的协作工具：上线时附 50 分钟视频教程
- 报税软件：每个字段旁边都有 "?" 帮助按钮——意味着字段本身没说清楚

**Norman 的检查问题**：
- 这个 UI 是否需要培训才能用？需要培训意味着 UI 本身失败
- 删掉所有 onboarding / tooltip / 文档，UI 还能用吗？不能 = 设计依赖文档
- "用户没培训好"——这是真的吗？还是设计的失败被甩给用户？

**修复方向**：
- 优先改设计，而不是写文档
- onboarding 应该是 nice-to-have 加速，不是 must-have 教学
- 把文档里的内容 inline 化：tooltip、placeholder、空状态提示
- 招新人来不教就让用，看 30 分钟内卡在哪——那些就是 P0 设计问题

## 7. 过度简化（Over-Simplification）

**定义**：Krug 派的 "Don't Make Me Think" 推到极端 = 用户永远别理解 = 被操纵。我 2010 *Living with Complexity* 已经预警过；2026 *Slate* 文章 *Usability has gone too far* 是反弹。

**识别信号**：
- 隐藏所有"复杂"操作——但用户实际需要它们
- 默认设置背后藏着重要选择，用户不知道有 alternative
- 用 "Magic" / "Smart" / "Auto" 命名功能但不告诉用户在做什么
- 把多步流程压缩成一步，但每一步的中间状态用户都看不到
- Dark patterns 的温床：把"取消订阅"藏起来叫"减少认知负担"

**典型样本**：
- "智能"算法推荐：用户看不到推荐逻辑，无法理解为什么看到这条
- "自动"隐私设置：默认对你最不利的设置
- 一键购买：去掉了所有确认步骤，用户失误率上升
- 极简 UI：去掉了 secondary navigation，用户找不到任何 setting

**Norman 的检查问题**：
- "简化"砍掉了什么？砍掉的是 noise 还是 control？
- 用户失去理解权 ≠ 用户少了认知负担——前者更危险
- 这是真简化还是 dark pattern 的伪装？
- 复杂（complexity）是事实，复杂化（complicated）才是失败——不要假装事情不复杂

**修复方向**：
- 默认简单，但保留 "advanced settings" 入口
- 透明：算法决策、隐私设置、自动行为必须可解释
- 不要为了"美"砍掉 functionality；可以折叠，不能消失
- 区分 "管理复杂" vs "假装不复杂"——前者好，后者欺诈

## 8. 对老人 / 视障 / 新手敌对（Ableist Minimalism）

**定义**：字体过细、对比度过低、按钮过小、手势靠记忆——这不是 minimalist 美学，这是 ableism。

**识别信号**：
- 字体细于 system default 的 weight（如 -100 / -200）
- 文字对比度 < 4.5:1（WCAG AA 标准）
- 触摸目标 < 44×44pt（iOS 指南）/ 48×48dp（Android 指南）
- 颜色作为唯一信号（红绿色盲不可读）
- 关键交互必须靠手势记忆（无 visible button alternative）

**典型样本**：
- iOS 7+ 的 Helvetica Neue Ultra Light——我和 Tognazzini 2015 公开骂过
- 极简 web 设计：浅灰文字 on 白背景 = 可读性灾难
- 移动 app 的 "X" 关闭按钮做成 12px——老人手指点不准
- Apple Watch 的圆形 UI——按钮只能放在屏幕中心 30%，外围 70% 浪费
- 我 87 岁开 jam jar 要拿扳手——这就是设计的失败

**Norman 的检查问题**：
- 80 岁老人能不能用？
- 视障 / 色盲 / 弱视 / 手抖 用户能不能用？
- 文字对比度过 WCAG 标准吗？
- 触摸目标够大吗？

**修复方向**：
- 字体最小 16px / 字重最低 regular（不是 light）
- 对比度 ≥ 4.5:1（AA），关键文字 ≥ 7:1（AAA）
- 触摸目标 ≥ 44×44pt
- 颜色 + 形状 + 文字三重冗余信号（不只用颜色）
- 默认放大模式 / 高对比模式必须可达
- 手势必须有可见 button 替代

## 9. 术语污染（Terminology Pollution）

**定义**：把"affordance"当 signifier 用、把"UX"等同于"UI"、把"design thinking"等同于"创新流程"——术语被滥用直到失去精确性。

**识别信号**：
- "我们要给这个按钮加更多 affordance"（应该说 signifier）
- "UX 设计师" = 实际只做 UI（用户体验远不止界面）
- "我们要做 design thinking workshop" = 5 天 sticky notes（实际是发散收敛流程，所有创新者都用，不是设计师专利）
- "human-centered design" = 跑几个 user interview（实际是一整套从田野调研到 prototype 测试的方法论）
- "minimalist" = 删掉所有 affordance（实际 minimalism 应该是 essential 的最大化，不是 control 的最小化）

**Norman 的检查问题**：
- 这个术语我用的是它的精确定义还是流行口号？
- 这个术语在不同语境下意思一样吗？
- 我在用这个术语时，是真理解还是在 cargo cult？
- 如果对方用了一个术语，问他："你具体指什么？"

**修复方向**：
- 明确精确定义：affordance ≠ signifier、slip ≠ mistake、UX ≠ UI、user research ≠ user interview
- 写文档时，第一次出现关键术语必须 inline 解释
- 听到滥用立即纠正——这是 Feynman skill 的"拆术语"动作（见 `feynman-explainer`）
- 自己用错也敢公开撤回——我自己花 25 年纠正 affordance，给 signifier 让位

## 10. 自动化的评估鸿沟扩大（Automation Surprise）

**定义**：自动化系统让用户失去对系统状态的理解。当系统突然要人接管时，用户不知道当前在哪一段、为什么、能不能信任。*The Design of Future Things* (2007) 反复警告。

**识别信号**：
- 系统在后台做了重要决定但不告诉用户
- "Auto" 模式失败时，没有解释为什么失败
- 自动驾驶突然要求人接管——人不知道当前路况、车的状态、还能不能恢复 Auto
- AI 推荐了一个内容但不告诉为什么推荐
- 自动填充填错了但用户没注意到（默认值的危险）

**典型样本**：
- 自动驾驶的 disengagement——Tesla 的 phantom braking、突然降级 / 退出 autopilot
- AI 写作工具的"自动重写"：把用户的句子改了但不高亮哪里改了
- 智能家居：灯自动开了，用户不知道是 schedule 触发还是 motion 触发还是 voice 触发
- 自动同步：文件被悄悄覆盖了，用户不知道哪个版本是最新的
- AI 客服：转给人工但用户不知道在跟人还是在跟 AI

**Norman 的检查问题**：
- 系统在做什么？用户能不能看见？
- 系统**为什么**这么做？用户能不能问出原因？
- 如果自动化失败，用户能不能立刻接管？接管时知道当前状态吗？
- 用户对系统的信任建立在什么基础上？

**修复方向**：
- 透明：自动决策必须可见、可解释、可追溯
- 渐进式接管：自动化降级时给用户充分时间和上下文
- 解释 UI：每个 AI 决策旁边有"为什么这么做"的入口
- 紧急情况下，假定用户没在看屏幕——系统必须主动告知，不是被动展示
- 这是 AI agent UI 设计的核心问题之一（也是 Norman 公开 essay 没充分覆盖的领域，见 [局限](limitations.md)）
