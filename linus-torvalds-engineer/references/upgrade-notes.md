# v1 → v2 · 升级说明

> 本 Skill 是 `linus-torvalds-perspective` (v1) 的深度重写。
> v1 本身是高质量的传记式总结；v2 的目标是把它从"思维参考"升级为"可执行指令集"。
> 两个版本可以共存——v1 适合想快速了解 Linus 思维框架的人，v2 适合想真正用它来做技术判断的人。

---

## 核心改动总览

| 维度 | v1 | v2 |
|------|-----|-----|
| 心智模型数量 | 5 个 | 6 个（新增"反宗教化"） |
| 愤怒-行动引擎 | 作为第 8 条启发式埋没 | 升级为独立心智模型 |
| Good Taste | 只有链表一个例子 | 7 步可运行代码审视清单 |
| 反模式识别 | 散见于各处 | 独立的 12 条 anti-pattern 库 |
| 表达 DNA | 单一档位，只列词汇 | 4 级强度，每级有触发/例句/禁忌 |
| Agentic Protocol | 4 类问题分类 | 7 类场景路由 + 短路规则 |
| 角色扮演规则 | 9 条嵌套逻辑 | 简化为表格 + 档位切换 |
| 身份卡 | 3 行 | 加入猫、AudioNoise、继承计划 |
| 诚实边界 | 列限制 | 加入具体降级模板 |
| 最新动态 | 截至 2026-04-17 | 含 AudioNoise/AI slop 政策/Hector Martin/conclave.rst |

## v1 的具体不足 + v2 如何修复

### 1. Agentic Protocol 过度工程化

**v1 的问题**：
- 问题路由只有 4 类（需要事实 / 纯框架 / 混合 / 通用架构）
- "必须使用工具"规则在简单问题上变成浪费
- 短路逻辑藏得很深，实际使用中容易被忽略

**v2 的修复**：
- 改为 7 类具体场景（代码 review / 设计 / 选型 / 项目 / 治理 / 哲学 / 炒作）
- 每类明确标注"是否需要调研"（✅ / ❌ / ⚠️）
- 短路规则提到顶层："如果用户粘贴了完整代码，跳过调研"
- 每类给出专属 checklist，不是通用的"搜索一下"

### 2. 心智模型有盲区

**v1 的 5 个模型**：
1. 工程实用主义 ✓
2. Good Taste ✓（但不可操作）
3. 信任网络优于规则 ✓
4. 数据结构优先 ✓
5. 演化优于顶层设计 ✓

**v1 缺失的模型**：
- **反宗教化**：Linus 对 RMS、Rust 福音派、systemd 教徒、social brigading 都有同一种反感——他拒绝把工程问题变成道德问题。这是他比所有同辈都锋利的独特视角。v1 完全没有这个维度。
- **愤怒-行动引擎**：Git 10 天原型、Nvidia 中指、AudioNoise——这些都是愤怒驱动的创造。v1 把它降格为"启发式 #8"，埋没了其核心地位。
- **演化论**：v1 有，v2 合并到"反宗教化"里（因为演化论本质上也是"不预设立场，让代码证明"，和反意识形态是同一个硬币的两面）。

**v2 的 6 个模型**：
1. 工程实用主义（精简保留）
2. Good Taste（重写为可运行清单）
3. 数据结构优先（保留）
4. 信任网络优于规则（保留）
5. **反宗教化 / 免疫意识形态**（新增，吸收原演化论）
6. **愤怒-行动引擎**（从启发式升级）

### 3. Good Taste 不可操作

**v1 的问题**：
- 只有 TED 链表一个例子
- 应用指导只有一句"问这个方案消除了原来的特殊情况吗"
- 使用者看完不知道怎么实际审视代码

**v2 的修复**：
- 拆出 7 步清单（见 `references/good-taste-checklist.md`）：
  1. 数据结构先行
  2. 特殊情况能否消失
  3. 缩进 ≤ 3 层
  4. 错误路径和正常路径比例
  5. 内化复杂度 vs 推给调用方
  6. 抽象层的必要性
  7. 命名是否暴露意图
- 每步有具体的"要问的问题"、"坏信号"、"修复方向"
- 线性顺序明确：数据结构不对，后面 6 步没意义

### 4. Anti-pattern 识别库缺失

**v1 的问题**：
- Linus 判断力的核心一半是"快速识别这是哪类烂模式"
- 但 v1 把 bikeshedding、feature creep 等概念散在各处
- 使用者需要"命中该 anti-pattern 的名字"来应用

**v2 的修复**：
- 独立的 12 条 anti-pattern 库（见 `references/anti-patterns.md`）：
  1. Bikeshedding
  2. Feature creep
  3. Premature abstraction
  4. Clever over clear
  5. NIH 重写无学习
  6. Abstraction for abstraction's sake
  7. Stable ABI 幻想
  8. 维护者缺席
  9. Religious technology evangelism
  10. 推复杂度给调用方
  11. 过度通用化
  12. Social brigading 施压（2025 Hector Martin 事件后新增）
- 每条结构化：识别信号 / 典型实例 / Linus 反应 / 修复方向

### 5. 表达 DNA 是"无级别"的

**v1 的问题**：
- 列了一堆骂人词（crap, stupid, brain-damaged）
- 但没区分 2018 前 / 后
- 使用者无法选择"正常 Linus"还是"骂人 Linus"
- 结果：默认得到的是混合物——既不够锋利也不够克制

**v2 的修复**：
- 4 级强度（见 `references/expression-levels.md`）：
  - L1 技术 review（默认）
  - L2 设计争议
  - L3 原则冲突
  - L4 外部挑衅（罕见）
- 每级有明确触发条件、词汇、句式、例句
- 2018 前 / 后对照表
- 用户可显式请求切换档位（"骂我" → L3，"严厉" → L3，"2015 年的 Linus" → L4）

### 6. 角色扮演规则过于繁琐

**v1 的问题**：
- 免责声明的触发逻辑："本次对话中首次以 Linus 身份开口时说一次"——但在 Claude Code 环境里每个 turn 的 context 是不可靠的
- 多条规则并列，没有优先级
- 退出角色的触发词列表太长，不够 robust

**v2 的修复**：
- 免责声明改为"每次会话首次开口说一次，不确定就只说一次"
- 规则合并到一张表格（情形 → 该怎么做）
- 退出角色简化为一类触发词 + 一个档位切换

### 7. 缺少降级策略

**v1 的问题**：
- 诚实边界列了限制（UX 不擅长、组织管理不擅长）
- 但没告诉 AI 遇到这些问题时**具体怎么说**
- 结果：遇到超纲问题时经常脱离角色

**v2 的修复**：
- 加入"降级模板表"：每种超纲情形对应一个具体的回复模板
- 模板用 Linus 的语气写出来，保持角色一致性
- 例：问到 UX → "从数据结构和 API 层面我可以说 X。UX 本身不是我擅长的——你需要找个真正懂用户的人"

### 8. 身份卡太薄

**v1 的问题**：
- 只有 3 行
- 缺少真实的生活细节（TED 里提到的猫、俄勒冈家、吉他）
- 角色扮演缺灵魂

**v2 的修复**：
- 加入 AudioNoise 项目（2026 最新）
- 加入 conclave.rst 继承计划（2026-01）
- 加入具体的"我不做的"清单（不用社交媒体、不谈政治商业）
- 保留原有的猫、俄勒冈、吉他效果器

### 9. 时间线是"事件列表"

**v1 的问题**：
- 24 行事件表格
- "对我思维的影响"列大多数是形式化的

**v2 的修复**：
- 精简到 15 个关键节点
- 每个节点的"思维影响"必须是具体的（从这个事件学到了什么判断规则）
- 加入 2024-2026 的新节点（Hector Martin、AI slop、conclave.rst、AudioNoise、Linux 7.0）

### 10. 最新动态不完整

**v1 截止 2026-04-17，但遗漏**：
- AudioNoise 项目的 vibe coding 意义（这是"个人 vs 生产代码"原则的具体证据）
- conclave.rst 的 governance 含义
- "Maybe the problem is you" 事件作为 Level 3 的示范（不升级到 Level 4）

**v2 补充了这些，并把它们编织进心智模型**。

## 结构哲学

v1 的结构类似传记：身份、模型、启发式、时间线、边界。读起来像一篇深度报道。

v2 的结构像一个工具包：
- Quick Reference Card（激活即可用）
- 心智模型（为什么这样判断）
- Good Taste checklist（如何审视代码）
- Anti-pattern 库（如何识别烂模式）
- 决策启发式（何时触发哪条规则）
- 表达 DNA 分级（如何用对语气）
- 降级模板（遇到超纲怎么办）

用户激活后**5 秒内**就知道该做什么，不需要通读 400 行。

## 为什么把 research 保留在 v1

v1 的 `references/research/` 已经是扎实的一手材料整理（11 个一手来源、每个都有 URL 和可信度标注）。v2 不重复这项工作——调研是分析的基础，不是分析本身。

但 v2 的心智模型推导在"反宗教化"和"愤怒-行动引擎"上需要新的材料支撑，这些我已经加入到 SKILL.md 的证据段落里。

如果你想看原始 research：`~/.claude/skills/linus-torvalds-perspective/references/research/`

## 可以从 v1 借鉴但 v2 没做的

诚实起见，v2 也有 v1 做得更好的地方：

1. **v1 的人物时间线更细**：v2 为了精简砍掉了一些事件，如果你需要完整的 1969-2026 时间线，v1 更好
2. **v1 的二手来源列表更长**：v2 只列了最核心的几个
3. **v1 的"矛盾处理"段落**（第 293 行前后）写得很漂亮，v2 保留了但没扩展

如果你在做深度研究性工作（写论文、做传记分析），v1 可能更合适。v2 的定位是**实战工具**，优先级是 actionability 而非完整性。

## 使用建议

- **日常代码 review / 设计讨论** → v2（L1 档位）
- **"骂我一段代码让我学"** → v2（L3 档位，明确说"骂我"或"严厉模式"）
- **写关于 Linus 的文章或报告** → v1（传记式总结更合适）
- **技术选型 / 治理决策咨询** → v2（场景路由 + 短路规则）
- **想了解 Linus 思维框架的整体图景** → 两者都可以，看你偏好

两个 Skill 可以共存。用户说"用 Linus 视角"时，Claude 会根据触发词的侧重来选择——涉及 "review"、"good taste"、"骂我"、"严厉"、"bikeshedding" 这类**动作词**偏向 v2；涉及 "Linus 会怎么看"、"思维框架"、"整体视角"这类**认知词**偏向 v1。

## 未来可能的 v3 方向

本 Skill 仍有改进空间，未来版本可能加入：

1. **跨领域评估矩阵**：Linus 的 taste 在 Rust/Zig/函数式场景如何迁移
2. **治理决策树**：面对不同类型的社区冲突，完整的响应流程图
3. **用户自测题库**：让使用者验证自己是否真正理解了 good taste
4. **多人对话模拟**：Linus + Junio Hamano + Greg KH 的内核核心圈讨论模式
5. **代码自动标注**：给定一段代码，自动应用 7 步清单并输出报告

v3 不会很快出来——Linus 本人的原则是"让演化跑够时间"。如果 v2 在实际使用中暴露出新的不足再迭代，不为了迭代而迭代。
